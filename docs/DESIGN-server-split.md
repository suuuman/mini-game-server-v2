# 서버 분리 설계 — 세션 서버 · 마을 서버

> **상태**: 🟡 설계 (2026-08-26)
> **저장소**: `mini-game-server-v2` — `mini-game-server-portfolio` 에서 파생
>
> **개정 이력**
> - 초안: 세션 · 마을 · **채팅** 3서버
> - **개정 1**: 락 설계를 갈아엎음 — 초안은 「락 든 채 DB 금지」를 락 범위 구분 없이 적용했다 (§7)
> - **개정 2**: **채팅 서버를 없애고 2서버로** — 「채팅」을 종류로 나누지 않고 통째로 옮긴 것이 잘못이었다 (§0)

---

## 0. 왜 나누는가 — 진단

현재 서버는 **`Zone` 이라는 개념 하나에 여러 역할을 겸하게** 했다. 어느 것이 문제였는지 가려낸다.

| `Zone` 이 겸한 역할 | 판정 |
|---|---|
| **스레드 배정 키** (`zone_id % N`) | ⛔ **문제.** 게임 개념이 라우팅 키가 되면 안 된다 |
| **거래 소유자** (`Zone` 이 `trades` 를 가짐) | ⛔ **문제.** 같은 존끼리만 거래된다 |
| **채팅 대상** (존 브로드캐스트) | ✅ **문제 아님.** 지역 채팅의 대상은 원래 공간이다 |

### ⛔ 초안의 진단을 하나 철회한다

초안은 *「`Zone` 이 채팅 채널과 공간, 두 역할을 겸했다」* 고 썼고 그래서 **채팅 서버를 따로 뒀다.**
그건 틀렸다. **「채팅」이라는 이름 하나로 성격이 다른 셋을 묶은 것**이 진짜 문제였다.

| 채팅 종류 | 대상 결정 근거 | 그 정보를 아는 곳 |
|---|---|---|
| **지역 채팅** | **공간(존)** | **마을 서버** |
| **전체 채팅** | 서버 전체 접속자 | **마을 서버** |
| 귓속말 | `player_id` | **마을 서버** (같은 서버 안) |

**셋 다 마을 서버가 이미 아는 정보다.** 채팅 서버로 옮기면 그 정보를 **복제**해야 하고,
복제하는 순간 동기화·시퀀스·유실 복구가 따라온다 — **없어도 되는 문제를 만드는 것이다.**

⇒ **채팅 서버를 두지 않는다.** 마을 서버 하나가 곧 **채널 하나**다.

### 진짜 나눠야 하는 경계

| | |
|---|---|
| **세션 서버** | 접속 이전의 일 — 누가 어느 서버로 갈지, 이미 접속해 있지는 않은지 |
| **마을 서버** | 접속 이후의 일 — 게임 전부 |

### 목표 구조

존은 **마을 서버가 소유한 위치 라벨 한 필드**로 축소한다.
스레드 배정 키가 아니고, 거래의 소유자도 아니다. **지역 채팅의 대상으로만 남는다.**
존 안의 실시간 이동 동기화는 **UDP** 로 가는 것이 맞지만, 이번 단계에서는 다루지 않는다.

## 1. 책임 경계

| 서버 | 소유하는 권위 | 기능 |
|---|---|---|
| **세션 서버** | **서버 레지스트리 · 접속 상태** | 서버 등록·헬스체크·배정, 중복 접속 차단, 예약 발급, 운영 명령 |
| **마을 서버** | **플레이어 상태 · 아이템 · 위치** | 이동(논리) · 거래 · 강화 · 인벤토리 · **채팅 전부** |

**권위는 한 곳에만 둔다.** 「player 42 가 지금 접속 중인가」는 세션 서버만 답한다.
마을 서버는 자기 접속자만 알고 전체를 판단하지 않는다.

⚠️ **귓속말은 같은 마을 서버 안에서만 된다.** 다른 채널 유저에게는 안 간다 — 한계로 받아들인다.
채널을 넘는 통신이 필요해지는 시점이 **채팅 서버를 다시 꺼낼 시점**이다.

## 2. 접속 흐름

```
 ┌────────┐
 │ 클라   │  세션 서버 주소는 설정으로 기본 보유
 └───┬────┘
     │ ① Login(player_id)
     ▼
 ┌──────────────┐   ③ Reserve(player 42)      ┌────────────┐
 │  세션 서버   │ ─────────────────────────>  │ 마을 서버A │
 │              │                              └────────────┘
 │ · 서버 목록  │   ② 중복 확인 → 필요시 Kick(동기)
 │ · 접속 테이블│
 └───┬──────────┘
     │ ④ LoginAck { 마을A 주소 }
     ▼
 ┌────────┐  ⑤ Enter(player 42)   ┌────────────┐
 │ 클라   │ ────────────────────> │ 마을 서버A │  ⑥ 예약 확인 → 수락
 └────────┘                        └─────┬──────┘
                                          │ ⑦ 접속/종료 보고
                                          ▼
                                     세션 서버
```

### 왜 「예약」인가 — 인증 대신

실서비스 인증은 이번 범위 밖이다. 대신 **예약(reservation)** 으로 효과의 일부를 얻는다.

- 세션 서버가 배정하면서 대상 서버에 **「player 42 가 올 것이다」**를 미리 등록한다 (만료 10초)
- 마을은 **예약 목록에 있는 접속만** 수락한다
- ⇒ 서명도 암호도 없이 **「세션 서버를 거치지 않은 접속」이 거부된다**
  > ⭐ **4단계에서 성립한다** — 이 커밋으로 마무리된다.
  > 마을은 `on_frame` 의 배정 스위치 진입부에서 `session.player_id != 0` 을 보고 아닌 세션을 끊는다.
  > 신원을 얻는 길은 예약을 소비하는 `kEnterReq` 하나뿐이다 — `kLoginReq` 직행 경로를 폐지했다(ADR-022).
  > 회귀 하네스도 가짜 세션 서버로 예약을 받아 붙는 구조로 바뀌었다.
  >
  > ⛔ **「거부」의 뜻을 정확히 좁혀 읽어야 한다** — 실제로 보장되는 것은
  > **「그 `player_id` 의 살아 있는 예약을 소비한 접속만 신원을 얻는다」**이지
  > **「세션 서버를 거친 그 소켓만 신원을 얻는다」가 아니다.** 인가되는 것은 **소켓이 아니라 값**이다.
  >
  > 구멍이 **둘**이고 성격이 다르다 — 둘 다 토큰 검증이 없다는 같은 뿌리에서 나온다.
  >
  > | # | 무엇을 우회하나 | 어떻게 |
  > |---|---|---|
  > | ① **신원 사칭** | 세션 서버를 **거치면서** | 세션 서버가 `SessionLogin` 의 `player_id` 를 그대로 믿는다 — 아무 값으로나 예약을 받아 낸다 |
  > | ② ⛔ **예약 탈취** | 세션 서버를 **아예 안 거치고** | 마을 포트에 직접 붙어 `Enter(player_id=N)` 을 보내면 N 의 살아 있는 예약을 **소비하고 입장한다.** `handle_enter` 는 body 의 `player_id` 만 보고(`frame_router.cpp:349-350` — 열어서 확인. 기존 인용 `:361`은 `consume_reservation` 호출부와 혼동된 것이었다 — body 를 읽는 자리는 그보다 앞이다), 예약 테이블에 **주인을 식별할 값이 없다**(`player_id → expire_at_ms` 뿐). `Reserve` 규약(`s2s_packet.h`)에도 그런 필드가 없다 |
  >
  > ⛔ **②는 위 「세션 서버를 거치지 않은 접속이 거부된다」를 직접 반증한다** — `player_id` 를 아는 상대에게는
  > 경로 우회조차 완전히 막히지 않는다. 진짜 주인은 도착해도 예약이 이미 소비돼 `kInvalidArg` 를 받는다.
  > 막으려면 예약에 **주인을 묶는 값**(토큰)이 있어야 하는데 그것이 곧 인증이라 이번 범위 밖이다.
  > ⚠️ **11단계 리뷰가 잡았다** — 그 전까지 이 문서는 ②를 모른 채 「거부된다」를 단정하고 있었다.
  >
  > ⛔ **3단계 시점에는 성립하지 않았다** — 그때는 `kEnterReq` 에서만 확인하고 직행 경로가 남아 있었다.
  > §13 의 3단계 완료 기준 문언이 **「성립」**이지 「미경유 접속의 거부」가 아니었던 이유다.
- ⇒ 나중에 진짜 인증이 필요해지면 흐름 ③ 앞에 계정 검증을 끼우면 되고 **구조는 안 바뀐다**

## 3. 중복 접속 차단 — ⚠️ 반드시 동기

현재 프로젝트가 한계로 적어 둔 것: *「로그인 서버 브로드캐스트가 비동기라 두 세션 공존 창이 열린다」*
**이번에 그 창을 닫는다.**

```
❌ 비동기
   Kick 요청 발송 → 곧바로 새 접속 허용
   ⇒ 옛 세션과 새 세션이 잠깐 공존 → 그 창에서 아이템 복사가 가능하다

✅ 동기
   Kick 요청 → 「끊었다」 응답 확인 → 그때 LoginAck 발급
   ⇒ 공존 창이 없다
```

> ⭐ **동기 Kick(ADR-024)으로 성립한다 — 이 커밋으로 마무리된다.** 구현된 「동기」의 실체는 응답
> 대기가 아니라 **테이블 게이트**다: 중복 발견 시 Kick 을 보내고 그 자리에서
> `kSessionLoginBusy` 로 거절하며, `LoginAck(Ok)` 는 접속 테이블에 그 player 항목이 없을 때만
> 나간다. 항목 제거는 마을이 실제 정리를 마친 신호(`PlayerLeave`)로만 일어나므로 「끊었다
> 확인 후 발급」이 그대로 성립하고 공존 창은 없다 — 상세·대기 정책 정정은 §16-4.

**브로드캐스트가 아니라 테이블 조회다.** 세션 서버가 접속 테이블을 갖고 있으므로:

| | 전 서버 브로드캐스트 | **세션 서버 테이블** |
|---|---|---|
| 중복 확인 | 전 서버에 질의 | **자기 테이블 1회 조회** |
| Kick 대상 | 전 서버 방송 | **해당 서버 하나** |
| 서버 수 증가 시 | 비용이 비례 증가 | 그대로 |

조건: 마을이 **접속·종료를 세션 서버에 보고**해야 한다(흐름 ⑦). 헬스체크 연결 위에 얹는다.

⚠️ **테이블과 실제가 어긋날 수 있다** — 서버가 죽으면 보고 없이 접속이 사라진다.
⇒ 헬스체크 실패 시 **바로 지우지 않고 `orphan` 으로 표시하고 유예를 둔다** (§5-3).

## 4. 서버 레지스트리와 헬스체크

### 등록

마을 서버는 기동하면서 세션 서버에 **connect** 하고 자기를 등록한다.

⭐ **이 레지스트리와 접속·예약 테이블은 전부 세션 서버의 프로세스 메모리다** — DB 를 쓰지 않는다.
§9 가 `db/` 를 「마을만 링크」로 못박았고, 세션 서버는 그래서 DB 계층을 링크하지 않는다.
재시작하면 테이블은 비고, 마을들이 재연결·재등록으로 다시 채운다(§5-2).

```
Register {
    ver       : 프로토콜 버전
    host,port : 클라가 접속할 주소
    capacity  : 정원
    current   : 현재 인원
}
```

**세션 서버를 먼저 띄운다.** 안 떠 있으면 마을은 재접속 백오프를 돌며 기다린다.

### 헬스체크

| 항목 | 값 |
|---|---|
| 주기 | **5초** |
| 실패 판정 | **3회 연속 무응답** → 배정 대상에서 제외 + 접속 항목 `orphan` 표시 (§5-3) |
| 내용 | 마을 → 세션. **인원 보고를 겸한다** |

인원 보고를 헬스체크에 실으면 **메시지 종류가 하나 줄고, 배정 정확도가 유지된다.**

### 배정 기준 — 정원 대비 비율

```
load = current / capacity        가장 낮은 서버를 고른다
```

단순 최소 인원은 **정원이 다른 서버가 섞이면 틀린다.** 라운드로빈은 이탈이 잦으면 편중된다.

## 5. 서버 상태 — 두 축은 직교한다

⛔ **초안의 「장애와 배포가 같은 경로가 된다」는 틀렸다.** 성격이 반대인 둘을 묶었다.

| | 드레인 | 세션 연결 끊김 |
|---|---|---|
| 성격 | **의도된 조작** | **장애** |
| 방향 | 종료를 향한 단방향 | **복구되어야 한다** |
| 발동 | 운영자 명령 | 아무도 원하지 않는다 |

세션 서버가 재시작 한 번 하면 모든 마을 서버가 드레인에 들어간다 —
**순단이 곧 전체 신규 접속 중단**이 된다. 그래서 두 축을 나눈다.

```
서비스 상태 (명령으로 전이)                  세션 연결 상태 (자동 복구)
  Running ⇄ Draining → Stopping → Stopped     Connected ⇄ Reconnecting
      ↑ 해제 가능                                   ↑ 무한 재시도
```

### 5-1. 드레인 — 운영 명령으로만 발동한다

⭐ **4단계에서 구현됐다 — ADR-023.** 아래는 설계 그대로 구현됐다(§8-3 스키마도 무변경).

용도는 **점검**과 **순차 패치**다.
**명령 경로** — 세션 서버가 운영 창구를 겸한다. 이미 연결이 있으니 별도 포트를 열지 않는다.
⚠️ **「운영자 → 세션 서버」는 구체적으로 세션 서버(`session.exe`)의 stdin 콘솔이다** —
`drain <server_id>`/`undrain <server_id>` 를 표준입력으로 받는다(빈 줄 = 종료). **원격 API 가 아니다** —
그 프로세스의 로컬 콘솔에 접근할 수 있는 사람이 곧 「운영자」다. 별도 인증·권한 경로는 없다.

```
운영자(세션 서버 stdin 콘솔) ──[drain <id>]──> 세션 서버 ──[SetMode(village-A, drain)]──> 마을 서버 A
                                              <──[SetModeAck + 현재 인원]────────────────┘
```

| 상태 | 새 접속 | 예약 수락 | 기존 접속 | 배정 대상 |
|---|---|---|---|---|
| `Running` | ⭕ | ⭕ | ⭕ | ⭕ |
| **`Draining`** | ⛔ | ⛔ | ⭕ **정상 서비스** | ⛔ 세션 서버가 제외 |
| `Stopping` | ⛔ | ⛔ | 강제 종료 | ⛔ |

**⭐ 해제가 된다.** 점검을 취소하면 `SetMode(running)` 으로 되돌린다.
드레인은 종료의 예고이지 종료 자체가 아니다.

**종료 조건**
1. 접속 인원 0 → 세션 서버에 `DrainComplete` 보고
2. 또는 **타임아웃** — 안 나가는 접속이 있으면 영원히 못 끈다. ⚠️ **구현에는 이 타임아웃을 재는
   자동 장치가 없다** — `DrainComplete` 는 인원이 정말 0 이 될 때만 나간다. 언제 강제 종료할지는
   **운영자가 직접 판단**한다 — 세션 서버가 받는 `SetModeAck{current}`·`Heartbeat` 로 잔여 인원 추이를
   보고, 너무 오래 안 빠지면 운영자가 직접 서버를 내린다(§18-7 판단 — 이 창구까지 자동화할 근거가
   없었다: 얼마나 오래를 「타임아웃」으로 볼지는 운영 정책이지 프로토콜이 답할 문제가 아니다)
3. 진행 중인 거래는 완료를 기다리거나 취소(장치 없이 자연 완료 — U5, ADR-023)

**순차 패치 절차**

```
① 새 버전 기동 → Register (Running)
② 운영자 → 세션 → 마을A : SetMode(drain)
③ 세션 서버가 마을A 를 배정 대상에서 제외 → 신규는 새 서버로만
④ 마을A 인원 0 → DrainComplete → 종료 → 패치 → 재기동 → Register
⑤ 마을B 로 반복
```

⚠️ **드레인 중에도 세션 서버 연결은 유지한다.** 인원 보고를 계속 보내야
운영자가 「언제 꺼도 되는지」를 안다.

### 5-2. 세션 연결 끊김 — 재연결로 복구한다

**서비스 상태를 바꾸지 않는다.** 마을 서버는 기존 접속을 정상 서비스하면서 재연결만 시도한다.

> **「신규가 안 오는 것」과 「신규를 거부하는 것」은 다르다.**
> 클라는 세션 서버를 거쳐야 주소를 받으므로, 끊긴 동안 신규는 **어차피 안 온다.**

| 항목 | 값 |
|---|---|
| 백오프 | 1s → 2s → 4s → 8s → … → **최대 30s** |
| 재시도 | **무한.** 마을 서버는 서비스 중이므로 포기하고 죽으면 안 된다 |
| 끊긴 동안 | 기존 접속 정상 · **예약 목록도 유지**(만료 10초 안에 들어올 수 있다) |

**⚠️ 끊긴 동안 접속/종료 보고를 못 보낸다 → 세션 서버 테이블이 어긋난다.**

**재연결 성공 시**

```
① Register (재등록)
② FullSync — 현재 접속자 전체 목록을 보낸다
③ 세션 서버는 그 서버의 기존 항목을 통째로 교체한다
```

증분 보고로는 못 맞춘다. **끊긴 구간의 변화를 모르므로 전체를 다시 보낸다.**

### 5-3. 세션 서버 쪽 — 끊긴 서버의 접속자를 어떻게 볼 것인가

서버가 진짜 죽은 것과, 서버는 살아 있는데 S2S 연결만 끊긴 것을 **구분할 수 없다.**

| 지우면 | 안 지우면 |
|---|---|
| 살아 있는 서버의 유저가 **다른 서버에 중복 접속** 가능 | 진짜 죽었을 때 그 유저가 **재접속을 못 한다** |

**절충 — `orphan` 표시 + 유예**

```
S2S 끊김
  → 배정 대상에서 제외 (신규 안 보냄)
  → 접속 항목은 지우지 않고 orphan 표시
  → 유예 30초
       재연결 → FullSync 로 정합 복구
       유예 초과 → 진짜 죽은 것으로 보고 항목 삭제
```

**유예 중에 그 유저가 재로그인하면?** Kick 을 보낼 수 없다(연결이 없다).

> **다른 서버로 배정하고 허용한다.** 옛 서버가 재연결하면 **그때 FullSync 결과를 보고 옛 세션을 Kick 한다.**
> 앞 문장(허용)은 동기 Kick 이, 뒤 문장(재연결 시 대조 Kick)은 그 후속이 구현했다(ADR-027 —
> FullSync 전량 교체가 타서버 소유 항목을 덮어쓰지 않고 그 목록을 발신 링크로 Kick 한다.
> ADR-024 결정 5 가 우려한 「처리 중 발신」 새 패턴은 실코드에서 login 경로의 뮤텍스 안
> 발신 선례와 동형으로 수렴했다).

가용성을 택한 것이다. 유저가 튕겼는데 못 들어오는 쪽이 더 나쁘다.
⚠️ **대가**: 유예 구간에 두 세션이 잠깐 공존할 수 있다.
정합성의 최종 근거는 **DB 트랜잭션**이지 이 테이블이 아니라는 전제 위에서 받아들인다.

## 6. 마을 서버 내부

### 6-1. 스레드 구조

```
accept ×1
I/O 워커 ×4        (유지 — 완료 수거 · 프레이밍 · 송신)
워커 ×N            (로직 + DB 통합 — 세션 직렬 큐를 도착 순서대로 비운다)
틱 ×1              (고정 30Hz — 세션 · DB · 명부를 안 만져 워커와 간섭이 없다)
예약 스윕 ×1       (예약 만료 회수 — EntryTable 뮤텍스 아래에서만)
로거 ×1
S2S 커넥터 ×1      (세션 서버 연결 · 재접속 · 헬스체크)
```

⚠️ **구현 확정 정정 — 아래 두 줄이 늘었다.** 초안은 다섯 줄이었는데 구현이 스레드 둘을 더 세웠다:
**틱**(ADR-025 결정 5 — 워커 겸용이면 DB 지연이 틱 지연으로 번져 원인 축이 섞인다) ·
**예약 스윕**(ADR-021 결정 12 — §18-3 의 「기존 스윕 스레드에 얹는다」가 물리적으로 불가능했다).
현재 스레드 전수와 각자 만져도 되는 것은 `docs/ARCHITECTURE.md` §1 표가 정본이다.

**`zone_id % N` 배정을 없앤다.** 존은 플레이어 레코드의 필드 한 개다.

### 6-2. 로직·DB 워커 통합

| | 분리(현재) | 통합(신규) |
|---|---|---|
| 홉 | `I/O → 존 → DB → 존 → 송신` (3홉) | `I/O → 워커 → 송신` (1홉) |
| 자원 | 로직 4 놀고 DB 4 바쁨이 가능 | 워커 N 을 유동적으로 |
| DB 순서 보장 | `player_id % N` 큐가 필요 | **동기 호출이 자동으로 보장** → 장치 삭제 |
| 세션 프레임 순서 | 존 스레드 고정이 보장 | ~~세션 락으로 보장~~ → **세션 직렬 큐로 보장**(구현 확정 정정 — ⛔ mutex 는 배타이지 순서가 아니다. 같은 세션의 두 프레임을 두 워커가 다투면 락 획득 순서는 스케줄러 몫이라 뒤집힌다. 세션당 「실행권 1개」를 큐에 올리고 워커가 그 세션의 직렬 큐를 도착 순서대로 비우는 구조가 순서를 큐 자체로 지킨다 — `send -Seq 3000` 이 회귀 판정자다) |

#### ⚠️ 격리 손잡이 = 커넥션 풀 크기

통합하면 DB 지연이 워커를 잡아먹는다. **풀 크기로 막는다.**

```
워커 N=8, 풀=4  →  동시에 4개만 DB 에 갇히고 4개는 로직을 계속 돈다
```

⛔ **조건: 대여 실패 시 블로킹 대기 금지.** ~~즉시 반환해서 재큐잉한다~~ →
**즉시 `kBusy` 로 응답하고 재큐잉하지 않는다**(구현 확정 정정 — 서버측 재큐잉은 같은 요청이
실패-재시도를 반복하는 기아를 데려오는 장치라 §18-7 을 통과하지 못한다. `kBusy` 는 「재시도
유의미」로 이미 규정돼 있어 재시도는 유저 손에 남는다. 관측은 `[POOL2] try_failed`).
(분리 시절엔 100ms 대기 후 `kBusy` 였다 — 통합 구조에서는 그 대기가 격리를 무너뜨린다)

풀 크기는 **설정으로 뺀다.** 정답이 아니라 손잡이다.

### 6-3. 채팅 — 타입 3종

```
ChatReq  { type:u8, target:u64(귓속말만), message }
ChatNtf  { type:u8, from:u64, message }
```

> ✅ **6단계에서 구현됐다** — `kChatReq(3)`/`kChatNtf(103)` 재정의 + `kChatAck(115)`(귓속말 실패
> 시에만 — kNoPeer) 신설. **`from`/`target` 은 둘 다 player_id 다**(초안이 안 정한 것을 구현이 확정 —
> ADR-026 결정 2): 귓속말 회신은 받은 from 을 그대로 target 에 되돌려야 하므로 두 필드가 동종이어야
> 하고, 명부(`entered_`)가 player_id 키라 O(1) 조회가 이 선택에서만 성립한다. 거래 지목용 session_id
> 는 `kZoneMembersNtf` 가 정본이다(그 메시지가 만들어진 이유가 그것이다 — `packet.h` 주석).

| 타입 | 대상 | 찾는 방법 | 비용 |
|---|---|---|---|
| **Zone** | 같은 존 | **존별 인덱스** | 존 인원 |
| **All** | 서버 전체 | `players` 전체 | **O(N)** |
| **Whisper** | 지정 `player_id` | 맵 조회 | O(1) |

#### 존별 인덱스

지역 채팅을 전체 순회 + 필터로 하면 O(N) 이 된다. `zone_id → 세션 목록` 인덱스를 둔다.

| | 인덱스 없음 | **존별 인덱스** |
|---|---|---|
| 지역 채팅 | O(N) | **존 인원** |
| 존 이동 | 공짜 | **인덱스 갱신** |

**존 이동이 채팅보다 훨씬 드물다.** 인덱스 쪽이 맞다.
갱신은 `players` 맵과 같은 락(§7 L1) 아래 둔다 — 둘이 어긋나면 안 되는 한 쌍이기 때문이다.

#### ⭐ 한 번만 직렬화한다 (§17)

5단계까지의 코드는 **수신자마다 재직렬화**했다 — 멤버마다 `send_msg` 를 부르고
그 안에서 헤더 인코딩 + 세션 락 + `vector` 복사가 일어났다.
전체 채팅 한 줄에 그것을 정원만큼 반복하면 못 버틴다.
✅ **6단계에서 ①이 구현됐다** — `frame_router.cpp` 의 통짜 프레임 헬퍼(`build_frame`)가
헤더+본문을 1회 조립하고 대상마다 `send_frame` 으로 같은 버퍼를 큐잉한다(복사 ②는 그대로 보류).

> **직렬화를 한 번만 한다.** 만든 바이트를 대상마다 복사해 넣는다.

⚠️ **복사까지 없애는 것(공유 버퍼)은 별개 최적화**이고, 채팅 규모에서는 이득이 불확실하다.
정량 근거와 판단은 **§17** 에 있다.

#### 송신 규칙

⛔ **락을 든 채 보내지 않는다.** 락 안에서 **대상 스냅샷**(홀드 건 포인터)만 뜨고, 락 밖에서 보낸다.
느린 클라 하나가 전체를 잡는 것을 막는다. (§7 규칙 2)

## 7. 락 설계

> ⛔ **이 절은 한 번 갈아엎었다.** 초안은 「락 든 채 DB 금지」를 **모든 락에 무차별 적용**했고,
> 그 대가로 논리적 점유 플래그·재검증 지점·RAII 가드·점유 시한을 줄줄이 만들었다.
> **락의 범위를 안 따진 것이 원인이다.** 그 격언은 **전역 락** 기준이다.
> 플레이어별 락은 **들고 DB 까지 가는 것이 맞고**, 그러면 위 장치가 전부 필요 없어진다.

### 7-0. 선행 결정 — 소유권

| 대상 | 소유자 | 수명 보장 |
|---|---|---|
| `Player` 데이터 | **`Session` 이 소유** | 기존 **`io_count`** 홀드가 그대로 지킨다 |
| `players` 맵 | 마을 서버 전역 | `player_id → Session*` **약한 참조**. 찾으면 곧바로 `acquire` |
| **존별 인덱스** | 마을 서버 전역 | `players` 와 **같은 락 아래** — 어긋나면 안 되는 한 쌍 |
| **`Trade`** | ⭐ **두 `Player` 가 직접 가리킨다** | 전역 맵을 두지 않는다 |

⭐ **`placement` 는 사라지지만 `io_count` 는 오히려 쓰임이 는다.**
맵에서 찾은 포인터를 락 밖으로 들고 나가려면 홀드가 반드시 필요하다.

### 7-1. 락 목록 — 2계층

```
Player A ──┐
           ├──> Trade        두 L2 를 잡으면 Trade 를 완전히 제어한다
Player B ──┘
```

전역 `trades` 맵을 없앤다. 지금 `Zone` 이 그 맵을 소유하는 건 **존이 소유자였기 때문**이고,
존이 위치 라벨로 강등되면 맵도 있을 이유가 없다. **거래는 두 당사자의 것이다.**

| 기호 | 대상 | 종류 | 보유 시간 | **든 채 DB** |
|---|---|---|---|---|
| **L1** | `players` 맵 + **존별 인덱스** | ~~`shared_mutex`~~ → **`std::mutex`** (구현 확정 정정 — 아래 각주) | **찾고 `acquire` 하면 즉시 놓는다** | ⛔ **금지** |
| **L2** | 개별 `Session`(=Player) | `mutex` (세션마다) | 작업 단위 전체 | ✅ **허용** |
| **R** | 예약 목록 | ~~별도 `mutex`~~ → **L1 과 같은 뮤텍스**(구현 확정 — `EntryTable` 이 명부·예약을 한 락으로. 예약 확인과 명부 등록이 Enter 한 시퀀스 안이라 나누면 그 사이가 새 창이 된다) | 아주 짧게 | ⛔ |
| **M** | 서비스 모드 | `atomic` (현재 bool — draining) | — | — |

> ⛔ **L1 종류 정정(구현 시 확정)** — shared_mutex 는 이 저장소의 실측(`bench.h` 「mutex vs
> shared_mutex」: 짧은 읽기 구간에서는 읽기 비율 99% 에서도 더 느렸다)과 L1 의 주 용법(찾고 즉시
> 놓기)이 정확히 그 불리한 구간이라 **평 mutex 로 확정**했다. 전체 채팅의 O(N) 스냅샷(긴 읽기)이
> 생기는 6단계에서 A11(존 인덱스 분리)과 함께 재평가한다 — 교체 지점은 별칭 한 곳이다.
>
> ✅ **6단계 재평가 완료 — 현행 유지로 닫혔다.** 스냅샷형 임계구역(순회+원소당 원자 증가)을
> 접속 상한 N=4,096 까지 재현 실측(`bench_roster_snapshot`)한 결과 최악 22.4μs 로 판정 기준(수백 μs)에
> 크게 못 미치고 shared_mutex 이득도 없었다(N=100 에선 1.39배 손해) ⇒ **std::mutex 유지 · 존 인덱스
> L1 안 유지(A11 닫음)** · 별칭(`app::EntryTable` 의 `RosterMutex`)도 이때 실제로 신설됐다. 수치·성립
> 조건은 ADR-026.

**획득 순서: `L1 → L2`.** 역순 금지. `R`·`M` 은 다른 락과 겹치지 않는다.

#### 왜 L2 는 DB 까지 들고 가도 되나

- **L2 는 플레이어별이다.** 그 플레이어를 건드리는 요청만 대기한다
- **유저는 한 번에 한 조작만 한다** — 경합이 애초에 거의 없다
- 거래는 두 사람만 대기하고, 그때 끼어드는 요청은 **어차피 거부돼야 할 것**이다
- ⇒ **대기하는 사람이 없는데 그 대기를 피하려고 장치를 만들 이유가 없다**

#### 그래서 없어진 것들

| 초안에 있던 것 | 지금 |
|---|---|
| 논리적 점유 플래그 | **불필요** |
| 재검증 지점 3곳 | **1곳으로**(§7-3-A) |
| 점유 누수 방지 RAII 가드 | **불필요** |
| 점유 시한 정책 (미정 과제였음) | **없어짐** |
| 전역 `trades` 맵 + 그 락 | **없어짐** |

**메모리 상태와 DB 가 한 임계구역 안에서 함께 바뀐다.** 「DB 가 최종 근거니까 괜찮다」에 기대지 않는다.

### 7-2. 절대 규칙

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | ⛔ **전역 락(L1·R)을 든 채 DB·송신·S2S 금지** | 하나가 막히면 전체가 막힌다 |
| 2 | ⛔ **어떤 락이든 든 채 송신하지 않는다** | `send` 가 상대 세션 락을 잡는다 → 중첩 · 느린 클라 하나가 전체를 잡는다 |
| 3 | ⛔ **어떤 락이든 든 채 S2S 를 보내지 않는다** | 같은 이유. **큐에 넣기만** 한다 |
| 4 | ⭐ **락 밖으로 포인터를 들고 나가려면 `acquire`** | 그 사이 세션이 소멸한다 |
| 5 | ⭐ **커넥션을 먼저 빌리고 그다음에 락을 잡는다** (§7-4) | 풀이 비면 **락을 든 채 대기**한다 |

### 7-3. 동작별 락 시퀀스

| 동작 | 시퀀스 | 비고 |
|---|---|---|
| **Enter** | `R`(예약 확인·제거) → `L1`(unique, `players` + 존 인덱스 등록) → 락밖: S2S `PlayerEnter` | 예약 없으면 거부 |
| **Leave** | `L1`(unique, 제거) → `L2`(자기 · 거래 있으면 상대까지) → 정리 · 상대 스냅샷 → 락밖: 통지 · S2S | ⭐ **L1 먼저 빼야** 다른 요청이 못 찾는다 |
| **JoinZone** | `L2`(자기 · 거래 중이면 상대까지, 거래 정리) → 놓음 → `L1`(move_zone 완전 이전 1회) → 락밖: 통지 — **확정** (아래 「구현 확정 정정」) | |
| **Chat (Zone)** | `L1`(shared, 존 인덱스에서 대상 스냅샷 + `acquire`) → **직렬화 1회** → 락밖: 송신 | |
| **Chat (All)** | `L1`(shared, 전체 스냅샷 + `acquire`) → **직렬화 1회** → 락밖: 송신 | O(N) |
| **Chat (Whisper)** | `L1`(shared, 대상 + `acquire`) → 락밖: 송신 | 없으면 실패 응답 |
| **Inventory** | **커넥션 대여** → `L2`(자기) → **DB** → 반영 → 놓음 → 락밖: 송신 | |
| **TradeReq** | `L1`(shared, 상대 + `acquire`) → **L1 놓음** → `scoped_lock(a,b)` → 양쪽 미거래 확인 + `Trade` 연결 → 락밖: 통지 | ⭐ **존 무관하게 거래 가능** |
| **TradeAnswer / SetItem / Cancel** | `scoped_lock(a,b)` → 상태 변경 + 스냅샷 → 락밖: 통지 | |
| **TradeConfirm** | **커넥션 대여** → `scoped_lock(a,b)` → 확인 → **DB(`sp_trade`)** → 반영 · `Trade` 해제 → 놓음 → 락밖: 통지 | ⭐ **재검증 없음.** 락을 놓은 적이 없다 |
| **Kick** (세션 명령) | `L1`(shared, 대상 + `acquire`) → 락밖: 종료 요청 → **즉시** 응답 | 동기 Kick — ⚠️ 「완료 콜백에서 응답」은 정정됐다(ADR-024 결정 6): 정합의 실제 게이트는 KickAck 가 아니라 뒤이어 나가는 `PlayerLeave` 이고(§8-2 멱등), 완료 통지 배선을 정당화할 손해가 없다(§18-7) |
| **Reserve** / **SetMode** | `R` 추가 / `M` atomic | |
| **Heartbeat 인원 보고** | **락 없음** — `atomic<int>` | |
| **FullSync** | `L1`(shared, 전체 스냅샷) → 락밖: 전송 | 청크 분할 |

#### ⚠️ JoinZone 이 두 락을 모두 건드린다

존을 바꾸면 **`Player::zone` 필드** 와 **존별 인덱스(L1)** 를 **둘 다** 고쳐야 한다.

> ⛔ **구현 확정 정정 — 결합 임계구역이 아니라 순차 분리다.** 초안은 「L1 을 쥔 채 L2 까지 잡는 한
> 임계구역」을 요구했는데, 그 요구의 전제가 직렬 큐 모델로 무효화됐다: ① `Session::zone` 필드는
> L2 가 아니라 **직렬 큐 직렬화**가 소유한다(그 세션의 실행권을 쥔 스레드만 읽고 쓴다) ② 인덱스와
> 명부 항목의 원자성은 `move_zone` 한 임계구역이 보장한다(옛 버킷 제거+새 버킷 등록+라벨 갱신이
> 한 번에 — **호출 지점도 하나다**: 나눠 부르면 「인덱스만 새 존」인 중간 창이 생긴다) ③ 거래와
> 존 인덱스는 독립 상태라 분리 실행의 중간 상태는 「취소 후 이동」과 관측 동치다 ④ 결합하면 L1
> 보유 시간만 늘어 §7-8 위험 1 을 키운다. 실제 시퀀스:
>
> ```
> L2(자기·거래 상대) 로 거래 정리 → 놓음
> → L1 로 move_zone(완전 이전 1회) → 놓음
> → 락밖: ack · 새 존/옛 존 브로드캐스트
> ```
> 두 임계구역이 중첩되지 않으므로 역순 획득 자체가 없다 — `L1 → L2` 규약과 충돌하지 않는다.

⚠️ **`L1` 을 잡는 동안 다른 모든 요청이 대기한다.** 존 이동이 드물다는 전제 위에서 받아들인다.
자주 일어나게 되면 **존 인덱스를 `players` 에서 떼어내고 별도 락으로** 내려야 한다 (미정 A11).

### 7-3-A. ⛔ 거래 상대를 알아내는 순환 — 유일하게 남는 재검증

`Leave`·`JoinZone` 에서 거래를 정리하려면 **상대 락도 잡아야 한다.**
그런데 **상대가 누군지 알려면 먼저 자기 락을 잡아야 한다.**

```
A 나감 : L2(A) 잡음 → Trade 보고 상대가 B 임을 앎 → L2(B) 를 잡으려 함
B 나감 : L2(B) 잡음 → Trade 보고 상대가 A 임을 앎 → L2(A) 를 잡으려 함
         ⇒ 데드락
```

`std::scoped_lock(a, b)` 는 **두 대상을 미리 알아야** 쓸 수 있는데, 여기서는 **하나를 잡아야 나머지를 안다.**

#### 해결 — `Player::trade` 를 락 없이 읽는다

```cpp
Trade* t = a.trade.load();              // 락 없이 읽는다 (atomic)
if (t == nullptr) return;
Player* b = t->peer_of(&a);
b->acquire();                            // 규칙 4 — 락 밖 포인터에는 홀드
std::scoped_lock lk(a.mtx, b->mtx);      // 두 대상을 알고 나서 한 번에
if (a.trade.load() != t) return;         // ★ 그 사이 바뀌었으면 포기
```

⭐ **재검증이 여기 하나 부활한다.** 다만 성격이 다르다 —
락을 놓고 DB 를 다녀와서가 아니라, **락을 잡기 전에 읽었기 때문**이다.

| | 초안의 재검증 | 여기의 재검증 |
|---|---|---|
| 원인 | 락 놓고 **DB 왕복** | 락 잡기 전 **미리 읽기** |
| 창의 크기 | 밀리초 | **마이크로초** |
| 확인할 것 | 여러 개 | **포인터 하나** |
| 개수 | 3곳 | **1곳** |

⚠️ **`Player::trade` 는 `atomic<Trade*>` 여야 한다.** 평범한 포인터면 이 절이 성립하지 않는다.

### 7-4. ⭐ 커넥션은 락보다 먼저 빌린다

```
❌  L2 잡음 → 커넥션 대여(풀이 비면 대기…) → DB → 놓음
✅  커넥션 대여 → L2 잡음 → DB → 놓음 → 커넥션 반납
```

대여에 실패하면 **락을 잡기 전에** `kBusy` 로 끝난다. 아무도 기다리지 않는다.
§6-2 의 「대여 실패 시 비블로킹 재큐잉」과 같은 규칙이다.

### 7-5. 락 보유 시간의 상한 = DB 타임아웃

L2 를 DB 왕복 동안 든다는 것은 **DB 가 느려지면 그 플레이어가 그만큼 묶인다**는 뜻이다.

| 항목 | 값 |
|---|---|
| 연결 타임아웃 | **3초** (`db_conn.h` 의 `MYSQL_OPT_CONNECT_TIMEOUT` 실측 — 구현 확정 정정: 초안의 「5초」는 실코드와 달랐다) |
| 쿼리 타임아웃 | **3초** (`MYSQL_OPT_READ_TIMEOUT`/`WRITE_TIMEOUT` 동일 — §16-3 도 함께 정정) |
| 데드락 재시도(1213/1205) | **락을 든 채 최대 3회**(`kTradeRetry` — 구현 확정. 상한 있음) |

⚠️ **이 값들을 안 정하면 「락 보유 시간에 상한이 없다」와 같다.**
⇒ L2 보유 시간 최악치 = 3초 × 재시도 3회 ≈ **9초** — 묶이는 것은 그 거래 당사자 둘뿐이고(L2 는
플레이어별·L1 무관), 실질 비용은 커넥션 슬롯 점유다(`[POOL ]`/`[POOL2]` 로 관측). 5초 상향은
실측 근거가 없어 하지 않았다.

### 7-6. 데드락 방지

| 상황 | 수단 |
|---|---|
| 거래 — 플레이어 락 2개 | `std::scoped_lock` — C++17 회피 알고리즘 내장. **id 정렬 불필요** |
| 계층 역순 (`L2` 든 채 `L1`) | 규약 `L1 → L2`. ⚠️ **컴파일러가 안 잡는다** |
| DB 락과 메모리 락의 교차 | DB 쪽은 `(player_id, item_id)` 오름차순(기존). 메모리 쪽은 `scoped_lock`. **두 세계가 섞이지 않는다** |

**검사 수단** — Debug 빌드에서 **스레드별 보유 락 계층 번호**를 `thread_local` 로 들고, 역순 획득 시 `assert`.
계층이 2개뿐이라 검사도 간단하다. ✅ **구현됐다** — `core/lock_rank.h`(`LockRankGuard` · NDEBUG no-op ·
`scoped_lock` 짝 획득은 가드 1개). 검증력은 역순 획득 뮤턴트가 `zone_race` Debug 회차에서 즉시 assert
발화하는 것으로 실측 증명됐다. ⚠️ **탐지 범위는 「한 스레드의 중첩 역순」뿐이다** — 두 스레드에 걸친
다단계 갱신의 중간 가시성(§7-3 JoinZone 정정 참조)은 검사기가 아니라 「단일 호출 지점」 규칙이 막는다.

### 7-7. 락이 필요 없는 것

| 대상 | 왜 |
|---|---|
| 접속 인원 카운터 · 서비스 모드 | `atomic` |
| 수신 버퍼 · 프레임 조립 | **세션당 I/O 는 항상 1개** — 기존 net 계층 불변식 |
| 로그 | 로거가 자체 큐를 갖는다 |

### 7-8. 남은 위험

| # | 위험 | 언제 | 상태 |
|---|---|---|---|
| 1 | **L1 경합 집중** | `Enter`/`Leave`/`JoinZone` + **idle 정리·Kick 정리도 같은 Leave 경로로 수렴한다**(구현 확정 추가 — 초안엔 앞의 셋만 있었다) | 완화책만. 총량 실측은 8단계 회귀·churn 에서 이상 무 — 정밀 계측은 A7 후속 |
| 2 | 계층 위반이 조용하다 | `L2` 든 채 `L1` | ✅ **검사기 구현**(§7-6 — 탐지 범위 한정도 거기 명시) |
| 3 | DB 지연 = 락 보유 지연 | DB 가 느릴 때 | ✅ **타임아웃 3초 확정**(§7-5 — 최악 9초 계산 포함) |
| 4 | `scoped_lock` try-lock 반복 | 거래 경합이 심할 때 | ⚠️ **안 쟀다** |
| 5 | 워커가 DB 대기로 소모 | DB 지연 시 | 풀 크기로 조절(`try_acquire` 즉시 실패 — §6-2) |
| 6 | 거래 상대 탐색의 재검증 누락 | §7-3-A | 재검증은 전 갈래 구현·⚠️ 결함 주입으로는 결정적 재현 불가(하네스가 못 덮는 것 — TESTING 참조). 유지 근거는 코드 정독 |
| 7 | ~~Kick 완료 대기에 상한 없음~~ | | ✅ **§16-4 로 해소** — 즉시 거절 |

**1번은 실제로는 덜 위험하다** — 자기 세션 처리에는 `L1` 이 필요 없다(이미 `Session*` 을 들고 있다).
`L1` 을 잡는 것은 **남을 찾을 때**(채팅·거래 요청·Kick)와 **명부가 바뀔 때**(Enter/Leave/JoinZone)뿐이다.

**7번 — 해소됨.** ⛔ 초안의 「강제 진행」은 §16-4 에서 **철회**했다. 기다리지 않고 거절하면 공존 창이 아예 안 생긴다.

## 8. S2S 프로토콜

### 8-0. 연결 위상

```
        ┌─────────────┐
        │ 세션 서버   │  accept 만
        └──────▲──────┘
               │  마을이 connect (양방향 전이중)
        ┌──────┴──────┐
        │  마을 서버  │
        └─────────────┘
```

| 결정 | 이유 |
|---|---|
| **마을이 connect** | 서버를 늘릴 때 **세션 설정을 안 건드린다.** 마을은 세션 주소 하나만 안다 |
| **하나의 연결로 양방향** | `Kick`·`SetMode` 를 **역방향 전송**한다. 세션이 마을 주소를 알 필요가 없고, 방화벽 규칙도 하나 |

⭐ **채팅 서버가 없으므로 S2S 연결은 이것 하나뿐이다.** 서버 간 상태 동기화가 존재하지 않는다.

### 8-1. 프레임 형식

```
클라  [ body_size:u16 ][ msg_id:u16 ]              [ body ]     헤더 4B · 본문 4,096B
S2S   [ body_size:u16 ][ msg_id:u16 ][ seq:u32 ]   [ body ]     헤더 8B · 본문 65,535B
```

| 항목 | 결정 | 이유 |
|---|---|---|
| 구조 | **길이 선행 · 빅엔디언 — 동일** | `frame_sizer` 를 프로토콜별로 주면 **net 계층이 그대로 재사용된다** |
| 헤더 | **S2S 는 `seq:u32` 추가** | 요청–응답 매칭 |
| 본문 상한 | **65,535B** | `FullSync` 가 4,096B 로는 부족. 형식은 안 바꾸고 상한만 올린다 |
| `msg_id` 공간 | **클라 `0x0000~0x7FFF` · S2S `0x8000~0xFFFF`** | 섞이면 **즉시 드러난다** |

⭐ `kMaxBodySize` 를 프로토콜별 상수로 분리한다. `static_assert` 도 프로토콜별로 하나씩.

⛔ **규약 상한(65,535B)과 세션 서버의 수신 한도(4,092B)는 다르다** (2단계 확정 — ADR-020 결정 2).
세션 서버는 마을의 S2S 연결을 기존 `IocpServer`+`Session` 으로 받는데 그 수신 버퍼가 **4,100B 고정**이고,
못 담는 프레임은 **끊기지도 않고 영원히 멈춘다**(net 의 함정). 그래서 수용 쪽 sizer 가 body > 4,092B 를
**규약 위반으로 즉시 절단**한다. ⇒ **`FullSync` 청크 body 는 4,092B 이하로 나눈다**(A12 확정값).
버퍼를 키우는 대안은 클라 세션까지 커져(1만 세션 x 65KB ≈ 655MB) 버렸다.

### 8-2. 요청–응답 매칭

| 규칙 | |
|---|---|
| **요청** | `seq` 를 발신자가 채운다 (연결마다 1부터, 0 은 예약) |
| **응답** | 요청의 `seq` 를 **그대로 되돌린다** |
| **단방향 알림** | `seq = 0` |
| **미지원 요청** | **`Unsupported{seq}` 를 반드시 보낸다** — 안 보내면 상대가 타임아웃까지 기다린다 |

#### ⭐ `seq` 는 방향별로 독립이다

양방향 연결이라 **양쪽이 각자 요청을 발신**한다. 마을이 보낸 `seq=5` 와 세션이 보낸 `seq=5` 가 공존한다.

**해결 — 메시지 종류가 방향을 결정한다.** 추가 필드가 필요 없다.

| | |
|---|---|
| `RegisterAck` · `HeartbeatAck` | **세션만 보낸다** → 마을은 자기 요청 테이블에서 찾는다 |
| `KickAck` · `SetModeAck` · `ReserveAck` | **마을만 보낸다** → 세션이 자기 테이블에서 찾는다 |

각자 **자기가 보낸 요청의 테이블만** 관리하고, 받은 응답의 `msg_id` 로 그 테이블을 조회한다.
⚠️ **응답 `msg_id` 를 양방향에 재사용하면 이 규칙이 깨진다.** 응답은 방향마다 다른 id 를 쓴다.

#### ⭐ 모든 요청은 멱등하게

재전송·재연결 후 중복 도착이 정상 시나리오다.

| 메시지 | 멱등성 근거 |
|---|---|
| `Kick` | 이미 없으면 **「없음」도 성공** |
| `Reserve` | 같은 `player_id` 면 **덮어쓴다** |
| `SetMode` | 같은 모드면 그대로 성공 |
| `PlayerEnter/Leave` | 같은 상태로의 전이는 무시 |

### 8-3. 메시지 목록

#### 마을 → 세션

| msg | body | 응답 |
|---|---|---|
| `Register` | `ver:u16, port:u16, capacity:u32, current:u32, host:str` | `RegisterAck{ server_id:u32, result:u8 }` |
| `Unregister` | — | `Ack` |
| `Heartbeat` | `current:u32` | `HeartbeatAck` |
| `PlayerEnter` | `player_id:u64` | — (알림) |
| `PlayerLeave` | `player_id:u64` | — (알림) |
| `FullSync` | `chunk_idx:u16, chunk_total:u16, count:u16, player_id[]` | `Ack` |
| `DrainComplete` | `remaining:u32` | — (알림) |

#### 세션 → 마을 (같은 연결의 역방향)

| msg | body | 응답 |
|---|---|---|
| `Reserve` | `player_id:u64, expire_ms:u32` | `ReserveAck{ result:u8 }` |
| `Kick` | `player_id:u64, reason:u8` | `KickAck{ result:u8 }` ⚠️ **동기** |
| `SetMode` | `mode:u8` | `SetModeAck{ current:u32 }` |

#### 클라 → 세션 (클라 프로토콜)

| msg | body | 응답 |
|---|---|---|
| `Login` | `player_id:u64` | `LoginAck{ result:u8, port:u16, host:str }` |

⚠️ **구현 확정 정정 — 필드 순서는 `result · port · host` 다.** 이 표가 한때 `host` 를 앞에 뒀는데,
`README.md`·`docs/ARCHITECTURE.md`·ADR-020 결정 4 가 전부 `port` 먼저다(가변 길이 `host` 가 마지막에 온다).
⛔ **이 표만 틀린 채로 남아 있었다.** 와이어 이름도 2단계에서 확정됐다 —
`kSessionLoginReq=12`(body `player_id:u64`) / `kSessionLoginAck=113`(body `result:u8 · port:u16 · host:str16`).

### 8-4. 검증 — 내부망이라도 뺄 수 없다

| 항목 | 규칙 |
|---|---|
| `body_size` | **상한 초과 즉시 연결 종료** |
| 고정 길이 메시지 | **`!=` 로 정확히** |
| 가변 길이 (`FullSync`) | `count` 와 실제 본문 크기 **일치** |
| 미정의 `msg_id` | ⭐ **무시 + 로그.** 끊지 않는다 |
| `seq` 중복 | 대기 중이 아닌 `seq` 의 응답은 무시 + 로그 |

**왜 미정의 msg_id 에 안 끊나** — 순차 패치 중에는 **새 버전이 구 버전에게 모르는 메시지를 보낼 수 있다.**
끊으면 배포 도중 연결이 무너진다. 클라 프로토콜에서 내린 것과 **같은 판단**이다.

### 8-5. 버전

`Register` 의 `ver:u16` = `major:u8 | minor:u8`.

| 상황 | 처리 |
|---|---|
| major 불일치 | **등록 거부** + 양쪽 로그 |
| minor 불일치 | **경고 후 진행.** 모르는 메시지는 §8-4 로 흡수 |

### 8-6. 타임아웃과 재연결

| 항목 | 값 |
|---|---|
| 일반 요청 타임아웃 | ⚠️ **미정** |
| `Kick` 타임아웃 | ✅ **폐지 — 대기 자체가 없다**(§16-4 정정). KickAck 매칭 pending 은 정리(억제 해제·집계) 용도라 기존 스윕 주기(`request_timeout_ms`)를 그대로 쓴다 |
| 재연결 백오프 | 1s → … → 30s · 무한 (§5-2) |

**재연결 시 in-flight 요청**

```
연결 끊김 → 대기 중인 모든 요청을 실패로 완료시킨다 (조용히 버리지 않는다)
          → 상위가 재시도 여부를 판단
          → 재연결 → Register → FullSync
```

⭐ **조용히 버리면 상위가 영원히 기다린다.** `JobQueue::push` 가 `bool` 인 것과 같은 이유다.
`seq` 카운터는 **연결마다 초기화**한다.

## 15. 관찰 수단 (C2)

> ⭐ **진단부터 고친다.** 「지표가 없다」가 아니라 **「지표는 있는데 죽어야 볼 수 있다」**이다.
> 이미 재고 있는 것: `[ALLOC]` `[POOL]` `[CONN]` `[NET]` `[POOL2]` `[TICK]` `[TICK2]`(p99 포함) `[SKEW]`.
> 전부 **종료 시에만** 찍힌다. ⇒ 만들 것은 지표가 아니라 **내보내는 경로**다.

### 15-1. 세션 서버가 곧 관제 지점이다

이 구조의 공짜 이점 — **마을이 이미 5초마다 `Heartbeat` 를 보낸다.**
거기에 지표를 실으면 **세션 서버가 전체를 보는 유일한 지점**이 된다. 추가 인프라가 0이다.

```
마을 A ──[Heartbeat + 지표]──┐
마을 B ──[Heartbeat + 지표]──┼──> 세션 서버 ──> [STAT] 로그
마을 C ──[Heartbeat + 지표]──┘         │
                                        └──> 운영 조회 응답 (SetMode 와 같은 경로)
```

| | |
|---|---|
| **해상도** | 5초 (헬스체크 주기). 순간 스파이크는 못 본다 |
| **대책** | 마을이 **5초간 집계**해서 보낸다 — `max`·`sum`·`count`. 보낸 뒤 리셋 |
| **비용** | ⭐ **연결도 주기도 이미 있다.** 메시지에 필드가 붙을 뿐 |

### 15-2. 3층으로 내보낸다

| 층 | 수단 | 용도 | 비용 |
|---|---|---|---|
| **1** | **각 서버가 N초마다 `[STAT]` 한 줄** | 그 프로세스 로그만 보면 된다 | **거의 0** |
| **2** | **`Heartbeat` 에 지표 첨부 → 세션이 전체 `[STAT]`** | 서버가 둘 이상일 때 **한 곳에서 본다** | 필드 추가뿐 |
| **3** | **운영 조회 명령** (`Stats` 요청/응답) | 지금 이 순간을 물어본다 | 메시지 1쌍 |

⛔ **HTTP 엔드포인트·Prometheus 는 안 넣는다.** 외부 의존 0 원칙이고, 이 규모에 과하다.
⛔ **별도 관리 포트도 안 연다.** 세션 서버 경로가 이미 있다.

### 15-3. 무엇을 볼 것인가

#### 마을 서버

| 분류 | 지표 | 출처 |
|---|---|---|
| **접속** | 동접 · peak · rejected | `[CONN]` (기존) |
| **역압** | **프레임 풀 사용률 · failed** | `[POOL]` (기존) ⭐ **가장 먼저 봐야 할 값** |
| **처리량** | 초당 프레임 수 · 워커 큐 깊이 | ⚠️ **신규** |
| **DB** | 풀 try_failed/open_failed | `[POOL2]` (기존) |
| **DB** | 쿼리 지연 avg/max | ⚠️ **신규** |
| **틱** | interval avg/p99/max · behind | `[TICK2]` (기존) |
| **송신** | **세션당 송신 큐 최대치** | ⚠️ **신규** — 큐 넘침이 조용히 버려지는 자리 |
| **락** | `L1` 대기 횟수/시간 | ⚠️ **신규** (§7-8 위험 1) |
| **S2S** | 연결 상태 · 재연결 횟수 | ⚠️ **신규** |
| **상태** | `Running` / `Draining` | ⚠️ **신규** |
| **메모리** | allocs/frees/bytes | `[ALLOC]` (기존) |

#### 세션 서버

| 분류 | 지표 |
|---|---|
| **레지스트리** | 등록 서버 수 · 상태별(Running/Draining/**orphan**) |
| **배정** | 로그인 요청 · 성공 · 거부(중복/정원 초과) |
| **중복 차단** | Kick 발생 수 · **Kick 타임아웃 수** ← §7-8 위험 7 이 실제로 나는지 |
| **접속 테이블** | 크기 · orphan 항목 수 |
| **서버별** | `current / capacity` = load |

### 15-4. 측정 비용 — 측정이 부하가 되면 안 된다

| 종류 | 방법 | 주의 |
|---|---|---|
| **카운터** | 스레드별 카운터 → 집계 시 합산 | ⛔ 공유 `atomic` 증가는 **캐시 라인 경합.** `alignas` 로 나눈다 (`LaneStat` 전례) |
| **게이지** | `atomic` 읽기 | 싸다 |
| **분포** | **avg · max 만.** p99 는 틱처럼 이미 재는 곳만 | 히스토그램은 과하다 |

⚠️ **핫패스 로그(`trace_frames`)는 끈다.** 카운터로 대체하는 것이 이 작업의 목적 중 하나다.
지금 「동작을 눈으로 보려고」 남겨 둔 로그가 **지표가 생기면 필요 없어진다.**

### 15-5. 임계 초과는 로그 레벨로

알람 시스템은 이 규모에 과하다. 대신 **임계를 넘으면 `[WARN]` 으로 올린다.**

| 조건 | 왜 |
|---|---|
| 프레임 풀 `failed > 0` | **역압이 실제로 걸렸다** |
| DB 풀 `try_failed > 0` | 풀이 모자라기 시작했다 |
| 틱 `max` 가 목표의 N배 | 밀리고 있다 |
| **송신 큐가 상한에 근접** | 조용히 버려지기 직전 |
| S2S 재연결 발생 | 세션 연결이 끊겼다 |
| **Kick 타임아웃 발생** | §5-3 의 공존 창이 실제로 열렸다 |

임계값은 **전부 설정으로 뺀다.** 지금 정할 근거가 없다.

### 15-6. 분산 디버깅 (D5) — 가장 싼 수단

서버가 둘이 되면 「이 요청이 어디서 막혔나」를 잇는 수단이 필요하다.
분산 추적(trace id 전파)은 범위가 과하다. **대신 이것만 한다.**

> ⭐ **모든 로그에 `player_id` 를 남긴다.**
> 세션 서버 로그와 마을 서버 로그를 **같은 `player_id` 로 grep 하면 흐름이 이어진다.**

`Login → Reserve → Enter → PlayerEnter` 가 한 유저 기준으로 두 로그에 걸쳐 순서대로 남는다.
비용은 로그 포맷 한 필드다.

### 15-7. 단계

| 단계 | 내용 | 붙는 곳 |
|---|---|---|
| 1 | 각 서버 **주기적 `[STAT]` 한 줄** | 기존 스윕/틱 스레드에 얹는다 |
| 2 | **`Heartbeat` 에 지표 첨부** | §8-3 메시지 확장 |
| 3 | **세션 서버 전체 `[STAT]`** | 서버별 한 줄 + 합계 |
| 4 | **운영 조회 명령** `Stats` | §5-1 운영 경로에 추가 |
| 5 | 임계 `[WARN]` · `player_id` 로그 | 전 구간 |

**1단계만 해도 「죽여봐야 안다」가 없어진다.** 나머지는 서버가 늘어날 때의 편의다.

### 15-8. 남은 미정

| # | 항목 |
|---|---|
| 1 | `[STAT]` 주기 — 5초? 30초? 로그량과 해상도의 균형 |
| 2 | 임계값 전부 |
| 3 | 락 대기 측정을 넣을지 — **측정 자체가 락 비용을 늘린다.** Debug 전용으로 둘지 |
| 4 | 지표 리셋 시점 — 보낼 때마다 리셋하면 「전체 누적」을 잃는다. 둘 다 둘지 |

## 16. 타임아웃 (A9 · A10)

### 16-1. 원칙 — 안쪽이 먼저 터져야 원인을 안다

```
innodb_lock_wait_timeout        DB 안의 락 대기
  <  쿼리 실행 예산
     <  read_timeout            클라이언트 소켓
        <  요청 전체 예산       애플리케이션 (재시도 포함)
           <  Kick 대기 / 클라 응답 대기
```

**각 층은 자기보다 안쪽 층보다 커야 한다.** 바깥이 먼저 터지면 **왜 실패했는지를 잃는다.**

### 16-2. ⛔ 지금 계층이 역전돼 있다 — 실제 결함

| 항목 | 현재 값 | 어디 |
|---|---|---|
| `connect/read/write_timeout` | **3초** | `db_conn.h:553` — ⛔ **하드코딩** |
| `innodb_lock_wait_timeout` | **50초** | ⛔ **설정 안 함 = MySQL 기본값** |

**락 대기가 50초까지 가는데 소켓은 3초에 끊긴다.**

```
거래 확정 → 행 락 대기 시작
  3초  : 클라이언트 소켓 타임아웃 → 「서버 연결이 끊겼다」 로 보고된다
  50초 : DB 는 그때까지 락을 잡고 있었다
```

⇒ **진짜 원인(락 경합)이 「연결 끊김」으로 가려진다.**
`DbConn` 은 질의 실패 시 스스로 재연결하므로, 로그에는 재연결만 남고 **락 대기는 흔적이 없다.**

⚠️ 값이 큰 것이 문제가 아니라 **원인을 잃는 것**이 문제다.

### 16-3. A9 — 값과 그 근거

**락 대기는 `MYSQL_INIT_COMMAND` 로 못 박는다.** 격리 수준을 박는 자리와 같다 —
`DbConn` 이 스스로 재연결하므로 **손으로 `SET` 을 보내면 그 경로에서 빠뜨리는 날이 온다.**

> ⚠️ **아래 표는 A9 의 「미구현 제안 패키지」다 — 현재 확정값이 아니다.** 락 2계층 구현은 이 패키지를
> 채택하지 않고 기존 실측값을 유지했다: `connect/read/write_timeout` **3초**(하드코딩 그대로) ·
> 데드락 재시도 **3회**(`kTradeRetry`) · `innodb_lock_wait_timeout` 미설정(MySQL 기본). 현재값의
> 정본은 **§7-5**(L2 보유 최악 ≈ 3초×3회 = 9초 계산 포함)다. 이 패키지를 채택하는 날 §7-5 도 함께 움직인다.

| 층 | 제안 기본값 | 근거 |
|---|---|---|
| `innodb_lock_wait_timeout` | **2초** | 게임 거래는 짧다. 2초를 넘게 기다릴 락이면 **이미 비정상** |
| 데드락 재시도 | **2회 · 즉시** | 각 시도가 짧아 백오프가 무의미. ⚠️ **락을 든 채 재시도한다** |
| `read/write_timeout` | **5초** | 락 대기 2초 + 실행 + 여유. **한 번의 쿼리** 기준 |
| `connect_timeout` | **3초** (유지) | |
| **요청 전체 예산** | **8초** | 재시도까지 포함. **⭐ 이것이 곧 `L2` 락 보유 상한이다** |

⭐ (제안 채택 시) **`L2` 락 보유 상한 = 요청 전체 예산 = 8초.** 최악의 경우 그 플레이어가 8초간 묶인다.
길지만, **DB 가 그만큼 아프면 이미 비정상이고 §15 의 `[WARN]` 이 먼저 뜬다.**

⛔ **전부 설정으로 뺀다.** 지금 3초가 하드코딩된 것도 같이 고친다.
⚠️ **이 값들은 「안전 쪽으로 크게 잡은 초기값」이다.** §15 의 지표로 실측한 뒤 조인다 —
`[POOL2]` 의 대기 분포와 쿼리 지연 max 가 그 근거가 된다.

### 16-4. A10 — Kick 은 기다리지 말고 거절한다

초안은 「타임아웃 초과 시 **강제 진행**」이라고 했다. **다시 보니 그럴 필요가 없다.**
그리고 ADR-024 결정 2 가 한 번 더 줄였다 — **2초 대기조차 하지 않는다.**

| | 초안 (강제 진행) | 1차 정정 (2초 대기 후 거절) | **구현 (즉시 거절)** |
|---|---|---|---|
| 유저 경험 | 최대 8초+ 대기 후 입장 | 2초 뒤 「잠시 후 다시 시도」 | **즉시 「잠시 후 다시 시도」** |
| 두 세션 공존 | ⛔ **창이 열린다** | ✅ 안 열린다 | ✅ **안 열린다** — 테이블 게이트(§3) |
| 클라 세션 홀드 | — | ⛔ **필요해진다**(세션 서버에 클라 세션 수명 경로 신설) | ✅ **불필요** — 무상태 유지 |

```
중복 발견 → Kick 발송(전용 pending 으로 재발신 억제) + 즉시 kSessionLoginBusy 거절
  클라 재시도 → 접속 테이블에서 항목이 지워졌으면(마을 PlayerLeave 도착) LoginAck 발급
             안 지워졌으면 다시 Busy — Kick 은 이미 나가 있다
```

2초를 버린 근거 — 그 대기가 사 주는 것이 「첫 재시도를 아낄 확률」뿐인데, 그 비용이
「클라 세션을 붙드는 새 수명 경로」다. 보안(복사 차단)은 예약 강제 이후 거절만으로 이미
성립하므로(ADR-024 맥락) 대기의 안전 이득이 없다.
⭐ **실측**: 재시도 폴링(500ms 간격)이 **1회째에 Ok** 를 받았고, 중복 감지에
필요한 `PlayerEnter` 전파 지연은 **관측 0회**(첫 Login 폴링부터 Busy)였다 — 「다음 시도는
이미 끊겨 있을 가능성이 높다」는 전제가 로컬 환경 실측으로 확인됐다(원격 환경은 안 쟀다).

#### ⭐ §5-3 의 orphan 과는 다르게 취급한다 — 상황이 다르다

| | orphan (§5-3) | Kick 타임아웃 (여기) |
|---|---|---|
| 상황 | 연결이 없어 **Kick 을 못 보낸다** | **보냈는데 응답이 늦다** |
| 기다리면 해결되나 | ✗ 30초 유예 후에도 안 오면 진짜 죽은 것 | ✅ **곧 끊긴다** |
| 선택 | **강제 진행** (가용성) | **재시도 유도** (안전) |

**「재시도하면 해결될 가능성」이 다르므로 선택도 달라야 한다.**
앞 절에서 「일관되게 강제 진행」이라고 쓴 것을 여기서 정정한다.

⇒ §7-8 **위험 7 이 해소된다.** Kick 타임아웃으로 인한 공존 창은 생기지 않는다.

### 16-5. 남은 미정

| # | 항목 |
|---|---|
| 1 | 클라 재시도 간격·횟수 — 3초 · N회? 무한 재시도면 서버가 계속 두들겨 맞는다 |
| 2 | 「진행 중」 거절이 반복될 때 — 몇 번째부터 유저에게 다른 안내를 하나 |
| 3 | 요청 전체 예산 8초의 실측 근거 — §15 지표가 쌓인 뒤 조인다 |

## 17. 브로드캐스트 비용 (A13)

> ⛔ **이 절은 한 번 갈아엎었다.** 초안은 「공유 버퍼로 복사를 없앤다」를 **필수**로 놓았는데,
> 정량으로 따져 보니 **채팅 규모에서는 이득이 불확실하고 작은 메시지에서는 손해일 수 있다.**
> 근거도 잘못 끌어왔다 — `DNF-GAP-ANALYSIS.md` 의 「200명 × 30Hz 스냅샷」은
> **위치 동기화 시나리오**지 채팅이 아니다.

### 17-1. 문제 — 같은 일을 N 번 한다

```
대상마다 :  ① 직렬화(헤더 인코딩 · 필드 배치 · 길이 계산)
            ② 세션 락
            ③ back 버퍼에 memcpy
```

전체 채팅 한 줄에 정원만큼 반복한다.

### 17-2. ⭐ 이건 두 개의 다른 최적화다 — 분리한다

| | 없애는 것 | 비용 | 판단 |
|---|---|---|---|
| **① 한 번만 직렬화** | ① 을 N 회 → 1 회 | **거의 0. 구조 변경 없음** | ✅ **지금 한다** |
| **② 복사 제거 (공유 버퍼)** | ③ 을 N 회 → 0 회 | 참조 계수 · 조각 목록 · 부분 송신 · 수명 관리 | ⚠️ **재보고 정한다** |

**①만 해도 대부분의 이득을 가져간다.**

```cpp
auto buf = serialize(msg);              // 한 번. 로컬 버퍼 하나
for (auto* s : targets) {               // 락 밖에서 스냅샷한 목록
    std::lock_guard lk(s->mtx);
    s->back.insert(s->back.end(), buf.begin(), buf.end());   // 복사는 그대로
}
```

직렬화는 **분기와 계산**이고 `memcpy` 는 **대역폭**이다. 전자를 N 번 안 하는 것이 실질 이득이며,
**송신 구조를 전혀 안 건드린다.**

### 17-3. ②를 지금 안 하는 이유 — 정량

메시지 54B · 100명 기준.

| | 비용 | 실제 시간 |
|---|---|---|
| `memcpy` 5,400B | 최신 CPU ~10GB/s | **약 0.5µs** |
| `refcount++` × 100 | **같은 캐시 라인 경합 → 순차화.** 각 20~100ns | **2~10µs** |

⛔ **작은 메시지에서는 공유 버퍼가 오히려 느리다.**
복사를 없앤 대가로 **캐시 라인 하나에 100번 몰리는 atomic 연산**을 만든 것이다.

| 시나리오 | 복사 총량 | 판단 |
|---|---|---|
| 채팅 54B × 100명 | 5.4KB | ❌ **이득 없음. 손해 가능** |
| 채팅 54B × 4,000명 | 216KB (~20µs) | △ 애매 |
| 스냅샷 4KB × 1,000명 | **4MB (~400µs)** | ✅ 확실한 이득 — **그러나 이번 범위 밖(UDP)** |

### 17-4. ②를 하게 되면 따라오는 문제 여섯

| # | 문제 |
|---|---|
| 1 | **참조 계수 경합** — §17-3 의 그 비용 |
| 2 | **메모리 수명이 길어진다** — 느린 클라 **하나**가 못 받으면 버퍼가 안 풀린다. 초당 수십 개면 누적 |
| 3 | **부분 송신** — `WSASend` 가 배열 중 일부만 보내면 **조각마다 offset 관리**. 지금은 offset 하나면 된다 |
| 4 | **발행 중 새 조각** — 이중 버퍼 스왑이 조각 목록 위에서 더 복잡해진다 |
| 5 | **누수 추적** — 참조 계수가 안 풀리면 누수인데 **누가 붙들었는지** 알기 어렵다 |
| 6 | **검증된 코드를 갈아엎는다** — 송신 경로는 이 프로젝트에서 가장 조심스럽게 만든 부분이다 |

⚠️ **2번이 얄궂다** — 아래 「느린 클라를 끊는다」 정책이 필요해지는 이유의 **절반이 공유 버퍼 자체**다.

### 17-5. ② 를 한다면 이렇게 — 설계는 남겨 둔다

실측이 손익분기를 넘으면 그때 쓴다.

```
세션 송신 큐 :  vector<Chunk>
                Chunk = { SharedBuffer* buf, offset, len }

발행         :  WSASend(sock, wsabufs, count, ...)     ← scatter-gather
```

⭐ **`WSASend` 는 원래 `WSABUF` 배열을 받는다.** 공유 버퍼를 `back` 에 append 하면 결국 복사라
의미가 없고, scatter-gather 로 보내야 **복사 없이 배치가 유지된다.**

**수명 — 참조 계수**

| 시점 | 동작 |
|---|---|
| 큐에 넣을 때 | `refcount++` (세션 `L2` 안) |
| 송신 완료 통보 | `refcount--` (I/O 워커) |
| 0 도달 | 풀에 반납 |
| **세션이 먼저 끊기면** | ⚠️ 큐에 남은 조각의 참조를 **전부 해제** |

⭐ **「커널에 맡긴 메모리는 못 움직인다」의 네 번째 사례**다
(세션 주소 · `compact` · 송신 `front` 재할당 · 여기). 참조 계수가 그것을 보장하는 장치다.

메모리 순서는 표준 패턴 — `fetch_add` relaxed, `fetch_sub` release, 0 을 관측한 쪽만 acquire 후 해제.

### 17-6. ⭐ 큐 넘침 정책 — 공유 버퍼와 무관하게 지금 넣는다

이건 **이미 있는 약점**이다. `send_chunks` 가 실패를 알려주는데
**채팅 브로드캐스트가 그 값을 버린다.** 소켓이 죽으면 I/O 실패로 정리되지만
**큐 넘침은 아무도 안 끊는다.**

| 단계 | 동작 |
|---|---|
| 1 | 큐 넘침 → **그 세션의 실패 카운터 증가** (§15 지표로 노출) |
| 2 | 큐 사용률이 상한의 일정 비율을 넘으면 `[WARN]` |
| 3 | **연속 실패가 임계를 넘으면 그 세션을 끊는다** |

**못 받는 클라는 이미 정상이 아니다.** 지금은 그 세션이 메모리를 문 채 남아 있다.
⚠️ 임계값은 **설정으로 뺀다.**

> ✅ **6단계에서 구현됐다** — 연속 실패 카운터(`overflow_streak` · 성공 시 리셋) · 3/4 수위 1회
> `[WARN]` · 연속 임계 도달 시 절단(`[net] send_overflow_limit` · 관측은 `[NET  ] send_full_kicked`).
> ⛔ **구현 확정 정정 — 킥은 기본 꺼짐(0)이고 마을만 config 로 켠다(8).** 이 킥의 절단은
> `session_gone` 콜백을 송신 호출자 스택에서 동기 실행하는데, 「테이블 뮤텍스를 든 채 링크로 send」가
> 허용 패턴인 세션 서버에서는 그 콜백이 같은 뮤텍스를 재획득해 자기 데드락이 된다(7단계 리뷰 발견 —
> ADR-026 「구현 결과」). 마을은 「어떤 락이든 든 채 송신 금지」(§7-2 규칙 2)가 서 있어 켜도 안전하다.

### 17-7. 락 순서 (§7 과의 관계)

```
L1(shared) 잡음 → 대상 스냅샷 + acquire → L1 놓음        ← 규칙 1·4
직렬화 1회                                                ← 락 밖
대상마다 : L2 잡음 → 큐에 추가 → L2 놓음                  ← 짧게
발행     : sending 플래그를 보고 하나만                    ← 기존 규칙
```

- **`L1` 을 든 채 직렬화하지 않는다** — 전역 락 보유가 길어진다
- 대상마다 `L2` 를 순차로 잡지만 각 보유는 마이크로초고, `L1` 은 이미 놓았다
- ⛔ **`L2` 를 든 채 `WSASend` 를 발행하지 않는다** (규칙 2)

**이 순서는 ①·② 어느 쪽이든 같다.**

| **지금** | **① 한 번 직렬화** + **§17-6 큐 넘침 정책** |

⚠️ **안 재고 ②를 넣으면 「재보고 정한다」는 이 프로젝트의 원칙을 어기는 것이다.**

> ✅ 「지금」 행의 둘은 **6단계에서 구현됐다** — ①은 §6-3 의 통짜 프레임 헬퍼, §17-6 은 연속
> 실패 킥(⛔ 기본 꺼짐·마을만 켠다 — §17-6 의 구현 확정 정정 참조). ②는 그대로 보류다.

## 18. 예약과 재접속 (A4 · A5)

### 18-1. 예약 수명

```
세션 → 마을 : Reserve(player_id, expire_ms)     기본 10초
클라 → 마을 : Enter(player_id)
              예약 있고 안 만료됐나 → 수락 + 예약 제거
              없거나 만료 → 거부 (클라는 세션 서버부터 다시)
```

**10초의 근거** — `LoginAck` 를 받고 마을에 connect 하는 데 걸리는 시간은 **수십 ms** 다.
10초는 넉넉하다. ⚠️ 그래도 **설정으로 뺀다** — 클라 환경이 나쁘면 달라진다.

### 18-2. ⭐ 예약도 정원을 차지한다

미정이던 것: **예약이 정원 계산에 들어가나.**

| | 안 넣으면 | **넣으면** |
|---|---|---|
| 결과 | **오버부킹** — 예약 100개가 한꺼번에 들어오면 정원 초과 | 만료까지 슬롯이 잠깐 묶인다 |

**넣는다.** 만료가 10초로 짧아 낭비가 제한적이고, 정원 초과가 더 나쁘다.

⭐ **다만 마을이 보고하지 않는다.** 세션 서버가 **자기가 발급한 예약을 세면 된다** —
발급한 쪽이 자기니까 이미 안다.

```
배정 판단 :  load = (마을이 보고한 current + 세션이 발급한 유효 예약 수) / capacity
```

⇒ **`Unreserve` 메시지가 필요 없다.** 취소하고 싶으면 세션 서버가 자기 테이블에서 지우면 된다.
마을 쪽 예약은 만료로 자연히 사라진다.

### 18-3. 만료 스윕

| 주체 | 방식 |
|---|---|
| **마을** | ⛔ **`app` 전용 스레드 1개를 둔다** (ADR-021 결정 12). 원래 이 칸은 *"기존 유휴 세션 스윕 스레드에 얹는다. 새 스레드를 안 만든다"* 였으나 **물리적으로 불가능**함이 확정됐다 — `iocp_server.h` 에 주기 훅이 없다(`set_drain_hook` 은 `stop()` 안에서 한 번만 불린다 · 호출 지점 전수 1곳) |
| **마을** | + `Enter` 처리 시 **lazy 확인** — 조회하는 김에 만료 판정 |
| **세션** | 자기 예약 테이블도 같은 방식 |

**주기 = 만료의 2~3배 (30초).** 만료 10초 + 스윕 30초면 최대 40초까지 남을 수 있는데,
항목당 수십 바이트라 **초당 100 로그인이어도 수백 KB** 다. 잦은 스윕이 더 낭비다.

⚠️ **정확성은 스윕이 아니라 `Enter` 의 lazy 확인이 책임진다.** 스윕은 메모리 회수용이다.

### 18-4. 재접속 — 케이스별

| 상황 | 정책 |
|---|---|
| **거래 중 끊김** | **거래를 취소한다.** 접속 종료는 이미 거래 정리 4지점 중 하나다. 상대에게 취소 통지 |
| **DB 작업 중 끊김** | `io_count` 홀드가 세션을 살려 두고, **작업은 끝까지 간다.** 결과를 보낼 곳이 없어 버려질 뿐 |
| ↳ 그래서 | ⚠️ **DB 는 이미 커밋됐을 수 있다.** 재접속 후 **인벤토리 조회로 확인**한다 |
| **재접속 경로** | **세션 서버부터 다시.** 마을 주소를 다시 받고 중복 체크도 다시 탄다 |
| **옛 세션이 아직 살아 있으면** | 세션 서버가 중복 감지 → **Kick** → §16-4 |
| **같은 마을로 가나** | **보장 안 한다.** load 기준으로 배정된다 |
| ↳ 지금은 문제없다 | 상태의 권위가 **DB** 라서 어느 서버든 같다 |
| ↳ ⚠️ 나중에 | **ADR-011(메모리 권위)로 가면** 「재접속은 원래 서버로」 정책이 필요해진다 |

⭐ **거래를 유지하고 재접속을 기다리지 않는다.** 아이템이 묶인 채 대기 상태가 남고,
그 대기에 또 타임아웃이 필요해진다. **취소가 단순하고 안전하다.**

### 18-5. 좀비 세션은 이미 있는 헬스체크가 정리한다

**`[net] idle_timeout_sec` 이 그 장치다.** 앱 레벨 ping/pong 으로 응답 없는 세션을 끊는 것이
그 기능의 본래 목적이고, **이미 구현돼 있다.**

> ✅ **4-b 단계에서 켰다 — ADR-023 결정 7.** 커밋 `config\server.ini` 의 `[net] idle_timeout_sec` 은
> 이제 **`90`** 이고 `0` 이 아니다(A15 의 「클라 ping 30s × 3회」에서 파생된 값이다).
> ⛔ 한때 이 자리에 *"지금 값이 `0`(꺼짐)인 이유는 회귀 하네스가 ping 을 안 보내기 때문"* 이라고
> 적혀 있었는데, **그 전제가 4단계에 사라졌다** — 자체 스폰 하네스가 스크래치 config 사본에
> `0` 을 덮어쓰게 바뀌어 커밋값의 영향을 안 받는다. `idle.ps1` 만 반대로 축소값 `2` 로
> 유휴 절단 자체를 시험하고, 사전 기동 갈래(`send`·`churn`)는 최장 유휴 0.8s 라 `90` 을 그대로 읽는다.
> 절차의 정본은 `docs/TESTING.md` §0 이다.

⇒ 할 일이던 **운영 기본값 정하기는 끝났다.**
설정 주석에 **「운영 기본값 / 테스트에서만 0」** 구분을 적는다.

⚠️ **이건 설계 과제가 아니라 값 하나다.** 없는 장치를 새로 만드는 것이 아니다.

### 18-6. 거래 타임아웃은 두지 않는다 — 푸는 문제가 없다

「`TradeReq` 후 상대가 응답을 안 하면 거래가 영원히 남는다」를 문제로 볼 뻔했다. **아니다.**

| 걱정 | 실제 |
|---|---|
| 거래가 오래 지속된다 | **정상 사용 패턴이다.** 협상하고, 아이템을 확인하고, 잠깐 자리를 비운다 |
| 상대가 응답 안 하면 내가 묶인다 | **내가 취소하면 된다.** `TradeCancel` 이 이미 있다 |
| 자원이 샌다 | `Trade` 객체 하나는 **수십 바이트.** 수천 개여도 무의미하다 |
| 영원히 남는다 | **세션이 끊기면 정리된다** (불변식 8 · §18-5 의 헬스체크) |

> ⭐ **유저가 스스로 벗어날 수 있으면 서버가 타임아웃을 걸 이유가 없다.**

서버가 임의로 취소하면 **거래창을 열어두고 대화하던 유저가 황당해진다.**
⇒ **불변식 8 의 정리 지점은 넷 그대로다.**

### 18-7. ⛔ 반복되는 실수 — 문제를 격상하기 전에 손해를 따진다

이 설계 과정에서 같은 실수를 여러 번 했다. **기록해 둔다.**

| 만든 장치 | 따져 보니 |
|---|---|
| 논리적 점유 플래그 | 락 **범위**를 구분하니 불필요 (§7) |
| 재검증 3곳 | **1곳**으로 (§7-3-A) |
| 채팅 서버 + 존 동기화 | **통째로 불필요** — 대상을 아는 곳이 이미 마을이었다 (§0) |
| 공유 버퍼 | 정량으로 보니 **이득 불확실** → 보류 (§17) |
| 거래 타임아웃 | **푸는 문제가 없다** (§18-6) |

**공통점**: 「이럴 수도 있다」를 문제로 격상시키고 장치를 만들었다.

**빠진 판단은 하나다 —**

> ⭐ **그게 실제로 누구에게 어떤 손해를 주나?**
>
> - 손해가 **없으면** 장치도 없다
> - 손해가 **유저가 스스로 벗어날 수 있는 것**이면 장치도 없다
> - 손해가 **자원**이면 **정량으로** 따진다 (수십 바이트인지 수 MB 인지)
> - 손해가 **정합성**이면 그때 장치를 만든다

⚠️ **장치는 공짜가 아니다.** 장치 하나가 새 실패 경로·새 미정 항목·새 위험을 데려온다.
실제로 논리적 점유는 「누수 방지 RAII」와 「점유 시한」이라는 과제를 낳았고,
공유 버퍼는 「느린 클라를 끊는 정책」이 필요한 이유의 절반이었다.
