# 던전앤파이터형 액션 RPG 서버 — 갭 분석과 작업 목록

> 전제: 「던전앤파이터를 모방한 게임」 = 2.5D 횡스크롤 액션 · 채널제 마을 · 4인 파티 인스턴스 던전 ·
> 장비 강화 기반 성장 · 경매장/우편/길드.
> 현재 서버(`mini-game-server`)를 그 목표까지 가져가려면 무엇이 있고 무엇이 없는가.
>
> ⚠️⚠️ **이 문서의 완료 표기·완료 서술(✅ 마크와 표 셀 안의 「완료됐다」·「폐기됐다」류 프로즈 전부)은
> 「그 작업이 `main` 에 머지된 시점」 기준이다.** 리뷰 중에 읽으면 아직 참이 아니다.
> ⛔ 이력: **처음 만들어질 때는 기준 시점 장치가 아예 없었고**(그때의 리뷰가
> *"배너 없는 문서에서 완료를 단정했다"* 고 잡아 배너가 생겼다), **그 배너도 「✅ 마크」만 좁게
> 커버해 표 셀 안의 완료형 프로즈가 범위 밖으로 읽힐 여지가 있었다** — 뒤의 리뷰가 그 스코프
> 모호성을 지적해 지금 문구(마크+프로즈 전부)로 넓혔다.

## 0. 한 줄 결론

**뼈대는 맞고, 내용물이 없다.**

지금 서버가 푼 문제는 「누가 무엇을 소유하는가」다 — 락 2계층(L1 명부·L2 세션) + 워커 직렬 큐 모델(⚠️
**정정** — 옛 「존 스레드 액터 모델」은 5단계가 존 스레드를 폐기하며 대체됐다. 「액터마다 스레드를
고정 배정한다」던 것이 「명부 락(L1) + 세션별 직렬 큐로 순서를 보장하는 공용 워커 풀」로 바뀌었을
뿐, 아래 결론의 논지 — 이 문제가 이미 풀려 있다는 것 — 는 그대로 유지된다) · 세션 수명 · 원자적 방
인계 · 트랜잭션 무결성. 이것들은 액션 RPG 서버에서도 **그대로 정답**이고, 대부분의 팀이 여기서 미끄러진다.

없는 것은 「게임」이다 — 좌표 · 시간 · 전투 · 캐릭터 · 성장. 그리고 그 위에 **규모의 문제**
(메시지 수백 개 · 마을 브로드캐스트 · 메모리 권위 + 지연 영속화)가 얹힌다.

## 1. 자산 — 그대로 가져가는 것

| 현재 구현 | 던파형 서버에서의 역할 | 재사용도 |
|---|---|---|
| ~~`placement` CAS 인계 (`[epoch][transit][zone]`)~~ | ⛔ **폐기됨(5단계)** — `app/placement.h` 가 삭제됐다. 이동 인계는 이제 `EntryTable::move_zone`(L1 명부 — unique lock)이 한 임계구역에서 끝낸다(ADR-025 결정 9) | ⛔ 이 행은 재사용 대상이 아니다 — 아래 대체 자산 참조 |
| ~~`zone_id % zone_thread` 액터 분할~~ | ⛔ **폐기됨(5단계)** — 존 스레드·`ZoneManager` 자체가 삭제됐다. 「존(인스턴스) = 스레드 배정」이라는 전제가 사라져 **「던전 인스턴스를 존 스레드에 배정한다」는 이 행의 재사용 논리가 성립하지 않는다** | ⛔ 이 행은 재사용 대상이 아니다 — 아래 대체 자산 참조 |
| ⭐ **대체 자산(5단계)** — L1 명부(`app::EntryTable` — 존 인덱스 `zone_index_`)·L2(세션별 `net::Session::game_mutex`)·워커 직렬 큐(`app::WorkerPool` — 세션당 실행권 1개로 순서 보장) | 던전 인스턴스는 이제 **스레드가 아니라 인덱스 값**(존 id)으로 구분된다 — 파티 단위 폐쇄 공간을 어떻게 나타낼지(존 id 네임스페이스 확장인지, 별도 인스턴스 키를 얹는지)는 **미확정**이다. 5단계 설계는 채팅 3종·존 인덱스 별도 락(A11)을 6단계 재평가 대상으로 명시했다 | ★★☆ 패턴은 있으나 던전 인스턴스 표현 방식은 재설계 필요 — 「그대로」로 단정하지 않는다(P7) |
| `io_count` 참조 계수 수명 | 세션이 (⚠️ **정정** — 존 스레드가 아니라) **워커 직렬 큐 실행권**·DB·타이머를 넘나드는 구조에서 필수(`entry_table.cpp` `acquire_hold`·`WorkerPool::submit` 이 각자 이 카운터를 올린다). 액션 서버는 이 경로가 훨씬 많아진다 | ★★★ 그대로 |
| `DbConn::trade()` (락 순서 정렬 · 재시도 · 감사로그 동일 트랜잭션) | **강화 · 구매 · 우편 수령 · 창고 이동 · 던전 보상 정산**이 전부 같은 패턴 | ★★★ 패턴 복제 |
| `post_write(player_id % N)` 순서 보장 | 캐릭터 단위 쓰기 직렬화. 아이템 복사 방어의 1차선 | ★★★ 그대로 |
| 길이 선행 프레이밍 · 프레임 풀 · 송신 이중 버퍼 | 와이어 계층 그대로 | ★★☆ 크기별 풀만 추가 |
| 고정 30Hz 틱 루프(⚠️ **정정** — 옛 `zone_thread_loop` 는 폐기됐다. 지금은 전용 `app::TickThread::run`) + 지터/behind 계측 | 시뮬레이션 루프의 **껍데기가 이미 있다.** 게임 틱 훅 자리는 아직 비어 있다(DNF Phase 1.2) | ★★★ 그대로 |
| 설정·로거·크래시덤프·부하 주입 스위치·회귀 하네스 문화 | 운영 기반 | ★★★ 그대로 |
| `bad_msg_score` · body 길이 검증 · 3중 수량 방어 | 치팅 방어의 출발점 | ★★☆ 확장 |

**즉, 3~6개월치 「어려운 부분」이 이미 되어 있다.** 아래 목록이 길어 보여도 대부분은 *어려운* 일이 아니라 *많은* 일이다.

## 2. 갭 — 축별 비교

### 2.1 도메인 모델 — ★ 가장 큰 구멍

| | 현재 | 필요 |
|---|---|---|
| 신원 | `player_id : u32` 하나 | 계정 → **캐릭터 N개** → 직업/전직/레벨/스탯/스킬트리/퀘스트/피로도 |
| 아이템 | `inventory(player_id, item_id, count)` | **스택형(소모품)** 과 **인스턴스형(장비)** 이 다르다 |
| 저장소 | 인벤토리 하나 | 인벤토리 · 장착 · 계정 창고 · 우편함 · 아바타 · 재료칸 |

> **⚠️ 현재 스키마로는 장비를 표현할 수 없다.**
> `PRIMARY KEY (player_id, item_id)` + `item_count` 는 「같은 아이템은 개수로 합쳐진다」는 전제다.
> 강화 +10 무기와 +0 무기는 같은 `item_id` 지만 **다른 물건**이다. 옵션·큐브·인챈트가 붙으면 더 갈라진다.
> → `item_instance(uid PK, owner_type, owner_id, item_id, enhance, options JSON, ...)` 로 **재설계**해야 하고,
> 소모품만 기존 스택 테이블에 남긴다. 이게 Phase 4 의 시작점이자 되돌리기 가장 비싼 결정이다.

### 2.2 공간과 시뮬레이션 — 통째로 없음

| | 현재 | 필요 |
|---|---|---|
| 좌표 | **개념 자체가 없다** | x(가로) · y(깊이) · z(높이) — 2.5D 벨트스크롤. 점프/공중콤보 때문에 z 가 필수 |
| 엔티티 | `Session*` 목록뿐 | 플레이어 · 몬스터 · 투사체 · 설치물 · 드랍아이템이 한 공간에 공존 |
| 상태 | 없음 | 상태머신(대기/이동/공격/피격/다운/부활/무적) · 경직 · 슈퍼아머 · 넉백 |
| 판정 | 없음 | 히트박스 겹침 · 프레임 단위 공격 판정 · 다단히트 · 무적 프레임 |
| AI | 없음 | 몬스터 어그로 · 패턴 · 경로 · 스폰 테이블 |
| 루프 | `Zone::on_tick()` **본문이 비어 있다** | 이 함수가 곧 게임이 된다 |

### 2.3 실시간 동기화 — 요청/응답만 있고 상태 동기화가 없음

현재는 **모든 메시지가 요청 → 응답**이다. 액션 게임은 반대다.

```
필요한 모양:
  클라 입력(방향키·스킬·공격) ─30~60Hz─> 서버 시뮬레이션(권위) ─30Hz─> 상태 브로드캐스트
                                                                   + 클라 예측 보정
```

없는 것: 입력 시퀀스 번호 · 서버 틱 타임스탬프 · 델타 스냅샷 · 클라이언트 예측/보간 규약 ·
지연 보상(lag compensation) 정책 · 재동기화(desync) 복구.

> **설계 결정이 필요한 지점**: 원작 던파는 클라이언트 권위가 강해서 핵·아이템 복사로 유명했다.
> 모방하되 **판정만은 서버 권위로 가는 것**이 이 프로젝트가 내세울 차별점이 될 수 있다.
> 다만 서버 권위는 틱당 비용이 몇 배로 뛴다 — 던전 인스턴스가 4인 폐쇄 공간이라 감당 가능한 규모다.

### 2.4 프로토콜 — 손 직렬화가 한계에 부딪힌다

| | 현재 | 필요 |
|---|---|---|
| 메시지 수 | 11개 (요청 8 + 응답 11) | **수백 개** |
| 직렬화 | `write_u32_be` 를 손으로 나열 | 그 규모에선 오프셋 실수가 반드시 난다 → **스키마 + 코드 생성** |
| body 상한 | 4096B (인벤토리 응답이 **이미 잘린다** — `kMaxRows`) | 캐릭터 전체 상태 · 마을 스냅샷은 확실히 넘는다 → 분할 전송 또는 상한 상향 |
| 버전 | 없음 | 클라 버전 협상 · 하위 호환 |

> 외부 의존 0 이라는 이 저장소의 원칙과 protobuf/FlatBuffers 도입은 충돌한다.
> **자체 IDL + 코드 생성기(파이썬 스크립트 한 장)** 가 현실적인 타협점이다.
> `.msg` 파일 → `packet_gen.h` 생성. 지금 손으로 쓴 11개도 그리로 옮긴다.

### 2.5 아키텍처 — 단일 프로세스의 한계선

| | 현재 | 던파형 정석 |
|---|---|---|
| 프로세스 | 1개 (accept 1 · IO 4 · 워커 8 · 틱 1) — ⚠️ **정정**: 옛 「존 스레드 4 · DB 4」구성은 존 스레드·전용 DB 워커 스레드가 Step 4 에서 삭제되며 소멸했다. DB 는 이제 워커 스레드가 직접 동기 호출한다(ADR-025) | 로그인 · 월드(채널) · 던전 · DB 게이트웨이 분리 |
| 서버 간 통신 | **없음** | 내부 RPC · 세션 핸드오프 · 전역 상태(중복 로그인·파티·귓말) |
| 확장 | 코어 수까지 (워커 수 늘리기 — `[app] workers`) | 던전 서버를 수평으로 늘린다 |

> **서두를 필요는 없다.** ⚠️ **정정** — 「존 스레드 모델」은 폐기됐지만 논지는 그대로 성립한다:
> 지금의 **워커 풀 모델**(공용 큐 + 세션별 직렬 큐)이 단일 머신의 멀티코어를 이미 쓰고 있고,
> 던전 인스턴스는 서로 독립적이라 프로세스 분리는 「나중에 라우팅만 바꾸면 되는」 일이다
> (DB 로그 스키마를 미리 분리해 둔 것과 같은 논리). Phase 6 으로 미룬다.

### 2.10 성능 — 코드 기준 구체 병목

지금 규모에선 문제없지만, 던파형에서 **반드시 걸리는** 지점들:

1. **이 커밋으로 재직렬화 자체는 없앴다 — 남은 것은 대상마다의 큐 복사다.** `handle_chat` 은 이제
   헤더+본문을 통짜 버퍼 하나로 한 번만 만들고(`build_frame` — §17-2 ①), 멤버마다 그 버퍼를
   그대로 `send_frame` 으로 재사용한다. 다만 대상마다 `send_chunks` 의 **세션별 뮤텍스 + `vector`
   복사**(그 세션의 `back` 에 이어붙이는 것)는 여전히 남아 있다 — **공유 버퍼(§17-2 ②)는 범위
   밖으로 보류됐다.** 4인 파티는 무시 가능하지만, **마을 채널 200명 × 30Hz 스냅샷**이면 그 복사
   비용이 남는다.
   → 그 복사까지 없애려면 한 번 직렬화한 버퍼를 참조 계수로 공유하는 경로(②)가 여전히 필요.
2. **`Zone::member_by_id` 가 선형 탐색.** 마을 규모에서는 `unordered_map` 필요.
3. **`JobQueue` 가 뮤텍스 + `std::function`** — 프레임마다 힙 할당. 입력이 초당 수만 건이면 부담.
   `core/mpsc_queue.h` 가 이미 있는데 안 쓰이고 있다 — 활용 여지.
4. **프레임 풀이 크기 하나(4100B)로 고정.** 액션 입력 패킷은 20B 남짓인데 4100B 를 문다.
   → 크기별 풀(small/large) 필요.
5. **핫패스 로그(`trace_frames`)** — 실서비스 규모에서는 반드시 끈다. 손잡이는 이미 있다.
6. **마을에 AOI(관심 영역)가 없다.** 던전(4인)은 불필요하지만 마을은 필요.

### 2.11 DB — 패턴은 맞고, 전략이 하나 빠졌다

현재는 **매 요청마다 DB 를 읽는다**(`kInventoryReq` → `select_inventory`).
액션 RPG 는 이게 불가능하다 — 전투 중 스탯/버프/HP 가 초당 수십 번 바뀐다.

> ⚠️ **ADR-014 가 바꾼 것과 안 바꾼 것을 헷갈리지 마라.**
> 조회·거래가 **저장 프로시저 경로**로 바뀌었고 서버 계정은 **`EXECUTE` 만** 갖는다.
> 그러나 **「매 요청마다 DB 를 읽는다」는 그대로다** — SP 는 왕복 **횟수**(거래 7→1)와
> **권한 모델**을 바꿨을 뿐, **읽는 빈도**를 바꾸지 않았다.
> ⇒ 아래 「메모리 권위 + 지연 영속화」는 **여전히 미해결**이다(ADR-011, 🟡 제안).
> ⭐ 오히려 SP 경로가 그 작업을 **쉽게** 만든다 — 영속화 지점이 SP 하나로 모여 있다.

→ **메모리 권위 + 지연 영속화**가 필요하다:
캐릭터 상태는 존 스레드 메모리가 권위, `dirty` 표시 후 주기적/이벤트성으로 저장 큐에 밀어 넣는다.
아이템 이동처럼 **소실되면 안 되는 것만** 즉시 트랜잭션(`trade()` 패턴).
그리고 서버 크래시 시 「마지막 저장 이후」가 날아가므로, 무엇을 즉시 쓰고 무엇을 미룰지가 설계 판단이 된다.

추가로 필요: 던전 클리어 보상 정산 · 경매장(**전역 경합이 심한 유일한 도메인** — `player_id % N` 샤딩이 안 먹는다) · 우편 · 랭킹.

## 4. 먼저 정해야 하는 설계 결정 4가지

코드보다 먼저 결정해야 하고, 나중에 뒤집으면 비싼 것들:

| # | 결정 | 선택지 | 권장 |
|---|---|---|---|
| 1 | **판정 권위** | 클라 권위(원작·가볍다·핵 취약) vs 서버 권위(무겁다·안전) | **서버 권위** — 던전이 4인 폐쇄 공간이라 감당 가능하고, 이 프로젝트의 차별점이 된다 |
| 2 | **아이템 표현** | 스택 단일 테이블 vs 인스턴스 분리 | **인스턴스 분리** — Phase 4 가 아니라 Phase 0~1 에 스키마만 먼저 확정 |
| 3 | **영속화 시점** | 즉시 쓰기 vs 메모리 권위 + 지연 저장 | **혼합** — 아이템 이동은 즉시 트랜잭션, 전투 상태는 지연 |
| 4 | **프로토콜 생성** | 손 직렬화 유지 vs 자체 IDL 코드젠 vs 외부 라이브러리 | **자체 IDL** — 외부 의존 0 원칙 유지, 규모는 감당 |
